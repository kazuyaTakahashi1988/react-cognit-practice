# 全体設計書

## 目的

小〜中規模前半で、現在の単純なディレクトリ構成を保ちながら責務の混在を防ぐ。

## 依存の方向

```text
app / router
    ↓
features
    ↓
components / lib / utils
```

- `app`: Provider、全体エラー境界、起動時処理など、アプリ全体の組み立てを管理する。
- `router`: URL、ページメタ情報、認証ガードを管理する。`features` のページを組み立ててよい。
- `features`: ユースケースまたは画面単位の UI、Hook、型を近くに置く。別の `feature` を直接 import しない。
- `components`: 複数画面から利用する、業務ルールを持たない UI を置く。
- `lib`: 副作用のない型、定数、スタイルを置く。
- `utils`: API、認証、Store、Analytics などの共通基盤を置く。単に置き場所が不明なコードは追加しない。

## 実装原則

1. 画面固有の処理は、まず対応する `feature` 内に置く。
2. 2 つ以上の画面で実際に必要になってから共通化する。
3. API クライアントは UI 状態を更新しない。ローディング表示は呼び出し側で選択する。
4. 想定内の API 失敗は `ApiResult`、想定外の例外は Error Boundary で最終的に捕捉する。
5. フォルダやライブラリは将来予測で追加せず、実際の複雑性が現れた時点で追加する。

## 中規模化の判断基準

次の状況が現れた場合のみ、ドメイン別 route 分割、サーバー状態管理、Role / Permission、API コード生成を検討する。

- 単一の設定ファイルでマージ競合が繰り返される。
- 同じ業務ルールが 3 つ以上の `feature` に重複する。
- API データのキャッシュ、再取得、楽観的更新を手作業で繰り返す。
- `auth | guest | public` で表現できないアクセス制御が必要になる。
